Мультитенантность на Postgres: как изолировать данные агентств через RLS

24.07.2026 · 9 мин · DETROYD SYSTEM GROUP

Когда одна база обслуживает сотни агентств, вопрос изоляции данных перестаёт быть архитектурным упражнением. Одна забытая проверка в одном запросе — и клиент видит проекты конкурента. Разбираем подход, при котором изоляция гарантируется базой, а не дисциплиной разработчика.

Три способа разделить арендаторов

ПодходИзоляцияЦена
База на арендатораПолнаяМиграции × N, дорогое обслуживание
Схема на арендатораВысокаяТысячи схем ломают инструментарий
Общие таблицы + RLSВысокая при верной настройкеДисциплина в политиках

Для SaaS с быстрым выпуском изменений третий вариант выигрывает: одна миграция применяется ко всем, а изоляцию обеспечивает сама СУБД.

Базовая конструкция

Каждая таблица с данными арендатора несёт agency_id. Профиль пользователя связывает учётную запись с агентством:

create table profiles (
  id          uuid primary key references auth.users(id),
  agency_id   uuid not null references agencies(id),
  role        text not null
);

create table projects (
  id          uuid primary key default gen_random_uuid(),
  agency_id   uuid not null references agencies(id),
  name        text not null,
  status      text not null default 'active'
);

alter table projects enable row level security;

Ключевая функция — определение агентства текущего пользователя. Её объявляют stable, чтобы планировщик вычислял её один раз на запрос, а не на каждую строку:

create or replace function current_agency() returns uuid
language sql stable security definer set search_path = public as $$
  select agency_id from profiles where id = auth.uid()
$$;

create policy tenant_read on projects
  for select using (agency_id = current_agency());

Три вещи, которые ломают изоляцию

1. Таблица без включённого RLS

Забыли enable row level security — таблица открыта всем. Это не гипотетический риск, а самая частая реальная утечка. Лечится не внимательностью, а проверкой в CI: запросом к pg_class находим все таблицы схемы public с relrowsecurity = false и роняем сборку.

2. Политика есть только на чтение

for select закрывает чтение, но insert, update и delete остаются без ограничений. Нужны политики на все операции, причём для записи важен with check — иначе пользователь сможет вставить строку с чужим agency_id или переписать своей записи владельца.

create policy tenant_write on projects
  for all
  using      (agency_id = current_agency())
  with check (agency_id = current_agency());

3. Функции с security definer

Такая функция выполняется с правами владельца и обходит RLS. Это нужно (например, чтобы отдать анониму несколько публичных полей настроек), но каждая такая функция обязана сама фильтровать данные и возвращать только явно разрешённый белый список полей. Обязательно указывайте set search_path — иначе вызывающий может подсунуть свою схему и подменить используемые функции.

Второй уровень: доступ к конкретным проектам

Изоляции по агентству мало. Внутри агентства монтажёр не должен видеть финансы, а фрилансер — все проекты. Появляется таблица участников проекта и режимы доступа: владелец видит всё, сотрудник — только назначенные ему проекты.

create policy project_scope on projects
  for select using (
    agency_id = current_agency()
    and (
      current_role_is_owner()
      or exists (select 1 from project_members m
                 where m.project_id = projects.id and m.user_id = auth.uid())
    )
  );

Здесь появляется неочевидная ловушка на клиенте. Если интерфейс строит список видимых проектов из данных, которые подгружаются параллельно другим запросом, возникает гонка: аналитика успевает посчитаться до того, как приехал состав участников, и показывает пустой экран или, наоборот, лишнее. Правило простое: зона доступа строится в том же запросе, который считает данные, а не берётся из общего состояния приложения.

Производительность

Условия политик попадают в каждый запрос, поэтому индексы должны их поддерживать. Практика:

  • Составные индексы, начинающиеся с agency_id: (agency_id, created_at desc), (agency_id, status).
  • Функции в политиках — только stable, иначе вызов на строку.
  • Проверяйте explain analyze от имени обычной роли, а не суперпользователя: у суперпользователя RLS не применяется и план будет другим.

Пагинация: ограничение, о котором забывают

PostgREST и подобные слои по умолчанию отдают ограниченное число строк — как правило, тысячу. Аналитика по журналу за полгода легко превышает лимит, и метрика молча считается по обрезанным данным. Ошибки нет, цифра есть, цифра неверная. Забор должен идти постранично через Range, с защитой от бесконечного цикла: если очередная страница начинается с той же строки, что предыдущая, значит прокси срезал заголовок — цикл нужно прервать.

Что проверять регулярно

  1. Все таблицы схемы имеют включённый RLS — автоматической проверкой в CI.
  2. На каждой таблице есть политики для чтения и для записи, у записи есть with check.
  3. Каждая security definer-функция фильтрует данные сама и имеет фиксированный search_path.
  4. Тест изоляции: пользователь агентства A под своим токеном не получает ни одной строки агентства B — по каждой таблице.

Как это устроено в DETROYD

Платформа построена на Postgres с RLS: все данные несут agency_id, доступ ограничен политиками на уровне базы, внутри агентства действует второй уровень — зона доступа по участию в проектах. Публичные данные (например, ссылки на странице входа) отдаются анониму через отдельную функцию с белым списком полей, сами настройки платформы при этом остаются закрытыми. Аналитические выборки забираются постранично, чтобы метрики не считались по обрезанным данным.
